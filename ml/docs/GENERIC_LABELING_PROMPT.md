# Промпт для разметки двух новых критериев (проверка generic evaluator)

Зачем: на контроле организаторы заменят один критерий через UI. Новый критерий оценивается generic evaluator
(`maestro/generic.py`), без встроенных правил. Чтобы измерить его точность, нужны метки по критериям, которых
пайплайн раньше не видел.

Как пользоваться:
1. Открыть Gemini Pro (не flash-lite — её мы проверяем).
2. Прикрепить `ml/data/reference/generic_dialogs.txt` (34 диалога).
3. Вставить текст ниже целиком.
4. JSON из ответа сохранить как `ml/data/reference/generic_reference.raw.json` или прислать в чат.
5. Человек из команды проверяет критерии из поля `uncertain`.

---

Ты — эксперт по контролю качества клиентской поддержки брокера Freedom Broker. В прикреплённом файле
`generic_dialogs.txt` 34 диалога. Оцени каждый по ДВУМ критериям ниже. Разметка станет эталоном для проверки
автоматической системы, поэтому важны точность и одинаковое применение правил ко всем диалогам.

## Как читать файл
Каждый диалог начинается со строки `=== <conversation_id> | <канал> | <язык> ===`, дальше реплики
`[номер] время роль: текст`. Роли: `client`, `operator` (его оцениваем), `bot`, `system`. Реплики бота и системные
события — контекст, не оцениваются. Диалоги `voice call` — расшифровка звонка с ошибками распознавания речи;
ошибки распознавания не считаются словами оператора. Диалоги на русском, казахском и английском.

## Критерий A. Извинение и признание проблемы (Да / Нет / N/A)
- Да — если клиент выразил недовольство или описал неудобство, оператор извинился или прямо признал проблему
  и предложил конкретный следующий шаг.
- Нет — клиент выразил недовольство или описал неудобство, но оператор не извинился и не признал проблему,
  либо признал, но не предложил никакого следующего шага.
- N/A — клиент не выражал недовольства и не описывал неудобства (просто задал вопрос).
- «Признал проблему» — оператор прямо показал, что понял неудобство клиента («понимаю, что это неудобно»,
  «вижу, что вывод не проходит»). Просто ответ на вопрос без этого — не признание.
- «Следующий шаг» — конкретное действие для клиента или от оператора (инструкция, передача специалистам, проверка).

## Критерий B. Понятность инструкций (0 / 5 / 10 / N/A)
- 10 — каждая инструкция оператора конкретна: куда нажать или что сделать, по шагам.
- 5 — инструкция есть, но без конкретных шагов или с пропущенным шагом.
- 0 — оператор должен был дать инструкцию, но инструкций нет или по ним невозможно действовать.
- N/A — оператору не требовалось давать клиенту инструкции (например, вопрос только про факт, или чат закончился
  до сути).
- Оценивай только конкретность инструкций. Тон, вежливость и правильность ответа здесь не учитываются.

## Общие правила
1. Каждый критерий оценивается строго по своему определению, независимо от другого.
2. Опирайся только на текст диалога и определения выше.
3. Для каждого диалога сначала коротко разбери оба критерия (какие реплики это показывают, с номерами),
   затем в самом конце выдай один JSON-блок со всеми 34 диалогами.

## Формат результата
```json
{
  "about": "Labels for two new criteria (A: apology and acknowledgement, B: clarity of instructions) on 34 DEV dialogs, made with <модель>; reviewed by: <кто проверил>.",
  "labels": [
    {"conversation_id": "p0-xx-000", "expected": {"A": "na", "B": 10},
     "notes": "Short reason in English for each non-obvious answer.", "uncertain": []}
  ]
}
```
Допустимые значения: A — `"yes"`, `"no"`, `"na"`; B — `0`, `5`, `10` или `"na"`. Числа без кавычек.
`p0-xx-000` — только пример формата, такого диалога нет. Размечай все 34 диалога, ничего не пропускай.

# Ревью точности `ml/`: что чинить и как мерить

Документ для агента, который будет править `ml/` (pipeline оценки чатов по чек-листу Freedom Broker).
Всё ниже основано на прогоне 19 размеченных DEV-диалогов (`data/reference/dev_reference.json`) через
текущий pipeline на трёх облачных моделях и на разборе каждой ошибки до конкретного probe.

## 1. Что уже сделано на ветке `ml/openai-comparison` (не закоммичено)

- `maestro/llm.py`: `OpenAIClient` с тем же интерфейсом, что `OllamaClient` (JSON-schema output, ретраи на 429/5xx,
  автоматически убирает `temperature`/`seed`, если модель их не принимает). Ключ берётся из `OPENAI_API_KEY`.
- `LLMClient.complete(..., think: bool | None = None)`: переопределение режима рассуждений на один вызов.
  У Ollama при `think=True` лимит ответа поднимается до `MAESTRO_THINK_PREDICT` (по умолчанию 4096), потому что
  текст рассуждений расходует `num_predict`. При старом `num_predict=384` ответы с рассуждением, скорее всего, обрезались.
- `maestro/probes.py`: `PROBE_CRITERION` (probe → критерий) и `think_for(key)`. Переменная `MAESTRO_THINK_ON`
  задаёт, где рассуждать: коды критериев (`04,06,07`), ключи probe (`summarized`), `generic` или `all`.
- `eval/run_dev.py`: флаги `--backend openai`, `--model`, `--workers N` (параллельные диалоги), `--think-on`,
  `--reasoning`, `--price-in/--price-out`, строка расхода токенов.
- Тесты: 61 проходит (добавлены 3: per-call think в payload Ollama, выбор think по критериям, поведение без переменной).

Примеры запуска:
```sh
uv run python eval/run_dev.py ../backend/data/dev_dataset.json --labels data/reference/dev_reference.json
uv run python eval/run_dev.py ... --labels ... --think-on 04,06,07
OPENAI_API_KEY=... uv run python eval/run_dev.py ... --labels ... --backend openai --model gpt-4.1-mini --workers 6
```

## 2. Найденные проблемы и исправления

Порядок — по пользе. Для каждого пункта: симптом на конкретном диалоге, причина, исправление, тест.

### 2.1 Баг: c04 засчитывает «запрос сформулирован» по любому «?» — ошибаются все модели

- Диалог `p1-ru-025`: клиент пишет боту «Здравствуйте, можно поговорить с человеком?», оператор здоровается,
  клиент уходит. Эталон c4 = `na`. Все модели дают балл.
- Причина: `rules.py`, `QUESTION = re.compile(r"\w[^?]*\?")` + `_settle_by_phrase(ctx, "request_formulated", client_ids, QUESTION)`
  в `c04`. Probe `request_formulated` решается регуляркой, модель вообще не спрашивается.
- Исправление: убрать регулярное «settle» для `request_formulated` или не засчитывать сообщения, где клиент только
  просит оператора/человека/специалиста («оператор», «человек», «специалист», «маман», «оператор қосыңыз», «agent», «human»).
  Формулировку probe `request_formulated` дополнить: «A request to talk to an operator or a human is NOT a request on substance».
- Тест: на транскрипте `p1-ru-025` (или его минимальной копии) c04 = `na`.

### 2.2 c02 уходит в N/A, не проверив, переспросил ли оператор уже известное — ошибаются все модели

- Диалог `p1-kz-008`: клиент назвал сайт ещё боту (#4 «Freedom Finance Global сайты»), оператор снова спрашивает
  «Қай сайтқа кірдіңіз?» (#9), клиент: «Жоғарыда жаздым ғой» (#10). Эталон c2 = `no`, все модели дают `na`.
- Причина: `rules.py`, `c02`: если `enough_info_from_start` = true, сразу `na`, и `used_known_details` не спрашивается.
- Исправление: сначала `used_known_details`. Если оператор переспросил то, что клиент уже дал, это `no`
  независимо от `enough_info_from_start`. Только если переспроса нет и данных хватало, ставить `na`.
- Тест: FakeLLM с `enough_info_from_start=True, used_known_details=False` → c2 = `no`.

### 2.3 Probe `summarized` слишком мягкий: модель считает итогом сам ответ

- Диалог `p1-en-001`: хвост оператора — ответ (#9 «A login stays on record… Use a different login») и
  «You're welcome. Take care!» (#11). Эталон c7 = `no` (только пожелание). Модели: `summarized = true` → c7 = `yes`.
  У gpt-4.1-mini так 7 из 7 ошибок на c7, у gpt-5.5 — 2.
- Причина: scope `operator_tail` (последние 3 реплики оператора) включает сам ответ, а вопрос
  «Does the operator sum up the outcome of the conversation?» не отделяет итог от ответа.
- Исправление:
  1. Для `summarized` и `offered_help` показывать только завершающие реплики оператора, после последней содержательной
     реплики клиента (или последнюю реплику оператора, если клиент после ответа писал только «спасибо»).
  2. Переформулировать: «Does the operator explicitly recap the outcome at the end, e.g. 'Итак, мы…', 'Подытожу…',
     'So, to summarise…'? Giving the answer itself is NOT a summary.»
- Тест: транскрипт «ответ + Take care!» → `summarized = false`, c7 = `no`.
- Связанное: в README уже отмечено, что формулировка c07 допускает два прочтения. Правило
  `(summarized or offered_help) and said_goodbye` оставить, пока нет эталона организаторов.

### 2.4 c06 оценивается одним холистическим вопросом — модели систематически завышают

- Модели ставят 10 там, где эталон 4 или 7; на `p1-ru-009`, `p1-ru-029`, `p4-ru-001` ошибаются все три.
- Причина: `LEVEL_PROBES["06"]` (`dialogue_level`) — один вопрос «выбери ступень», модель отвечает «на глаз».
- Исправление: разбить c06, как остальные критерии, на boolean-probes и собрать ступень кодом:
  - `client_had_to_ask_again`: клиенту пришлось переспросить или повторить из-за формулировок или порядка ответов
    оператора (пример: `p1-ru-009` #14 «Я спрашиваю, почему вывод ограничен»);
  - `unannounced_wait`: было явное ожидание без предупреждения (подсказка — `facts.long_pauses`);
  - `incoherent`: реплики бессвязные или противоречат друг другу.
  Правило: `incoherent` → 0; `client_had_to_ask_again` → 4; одна заметная накладка (`unannounced_wait` или другой
  единичный сбой) → 7; иначе 10.
- Вопрос к команде до реализации: в эталоне `p1-kz-008` c6 = 7, хотя клиенту пришлось повторить.
  Нужно договориться, когда переспрос — это 4, а когда 7, иначе правило будет спорить с разметкой.
- Тест: FakeLLM-сценарии на каждую ступень.

### 2.5 c05 проверяет реакцию только на одну жалобу

- Диалоги `p1-ru-009` и `p1-en-014`: эталон c5 = `no`, все три модели `yes`. В `p1-ru-009` на первую жалобу оператор
  реагирует, а на «Я спрашиваю, почему вывод ограничен» (#14) отвечает «Передам вопрос на проверку. До свидания.»
- Причина: `client_complained` возвращает одну реплику, `reacted_to_problem` спрашивается только про неё.
- Исправление: формулировка `reacted_to_problem` → «Did the operator respond to EACH complaint or concern the client
  raised? Answer false if the operator ignored or brushed off any of them.» Подставлять все реплики клиента с недовольством
  (или убрать `{complaint}` и показывать весь чат). Альтернатива — отдельный probe `ignored_complaint`.
- Тест: две жалобы, на вторую оператор не отвечает → c5 = `no`.

### 2.6 c03 и c08 решают одно и то же независимо и могут противоречить

- Раскрытие данных счёта до идентификации проверяют и c3 (`identification_required` + `identity_confirmed_first`),
  и c8 (`confidential_disclosure`) — разными вызовами модели. В `p1-en-001` gpt-4.1-mini поставила
  `confidential_disclosure = true` при c3 = `na`.
- Исправление: часть c8 «данные этого клиента до подтверждения личности» выводить из фактов c3
  (идентификация требовалась, данные раскрыты, подтверждения не было). Probe `confidential_disclosure` оставить только
  для данных другого клиента и внутренней информации компании.
- Тест: c3 = `na` → c8 не может стать `yes` из-за раскрытия данных клиента.

### 2.7 Спорная разметка — решить командой, не кодом

- `p1-ru-018`: оператор пишет «Сейчас точно биржа отменяет ваш приказ, ничего не сделать» без проверки.
  gpt-5.5 и gpt-5.4-mini считают это раскрытием информации по счёту (c3 = `no`, c8 = флаг), эталон — c3 = `na`, c8 = `no`.
- Если оставляем эталон: в `identification_required` дописать «A guess by the operator without looking at the account
  does not count as revealing account information».

## 2.8 Статус: 2.1, 2.2, 2.3 и 2.5 уже внесены на этой ветке

- `rules.py`: `OPERATOR_REQUEST` — просьба позвать оператора больше не засчитывается как запрос по «?» (2.1);
  `c02` сначала спрашивает `used_known_details`, переспрос уже данного → `no` (2.2).
- `probes.py`: новый scope `operator_closing` (реплики оператора после последней реплики клиента) для `summarized`

- Тесты: 64 проходят, добавлены 3 (оператор-просьба → c4 `na`, переспрос → c2 `no`, scope `operator_closing`).

## 2.9 Итерация 2: c06 по фактам, разметка, Gemini

Изменения:
- c06 (пункт 2.4) реализован: probes `incoherent` (→ 0, только с цитатой оператора), `client_asked_again` (→ 4),
  `noticeable_lapse` (→ 7), иначе 10; ступень ставит `rules.c06`. Оба вопроса про переспрос и сбой видят чат только
  с первой реплики оператора (scope `since_operator`), иначе просьба к боту «подключите оператора» считалась переспросом.
  Переспрос = вопрос о том же, на что оператор только что ответил, потому что ответ был непонятен; новый вопрос,
  возражение клиента или неверный ответ не считаются. Грубость и нарушения из c08 в c06 не учитываются.
- `impolite`: краткий или разговорный тон и неверный ответ — не грубость.
- Разметка (`dev_reference.json`, с пояснением в `notes`): `p1-ru-018` c3 na → no (вопрос про свои приказы, как в

- `OpenAIClient` работает и с OpenAI-совместимым API Gemini (`MAESTRO_OPENAI_URL`), разбирает его формат ошибок.

## 2.11 Логические конфликты (аудит rules.py) — исправлено

1. **Переформулированный критерий получал старую логику.** `match_standard` сравнивал тексты по символам с порогом 0.75,
   а смысловые правки почти не меняют похожесть («подтверждена» → «не подтверждена» — 0.98, «или» → «и» — 0.98).
   Теперь встроенная логика только при точном совпадении после нормализации (метка «Да —», пунктуация, хвост
   «по шкале», фраза «Нет — …»); любая другая формулировка — generic evaluator. Тексты из `frontend/mocks/checklist.default.json`
   и `data/default_checklist.json` распознаются как стандартные (тест). **Риск для интеграции:** если бэкенд пришлёт
   текст критерия в другом виде, критерий тихо уйдёт в generic — проверяйте `method` в ответе (`run_dev.py` печатает `methods`).
2. **c03: оператор сделал всё правильно, но получал «Нет»** (клиент отказался от проверки). Если оператор запросил проверку
   (`VERIFICATION_ASKED`) и не раскрыл данные счёта (новый probe `account_info_disclosed`) — «Да».
3. **c01: ложное «Да» для казахского без казахских букв.** `ChatFacts.dialog_language` из запроса; если диалог помечен
   другим языком, чем определился у оператора, решает модель.
4. **c02: предложение помощи в конце засчитывалось как уточнение.** Завершающие обороты («чем ещё могу помочь»,
   «басқа сұрақ», «anything else») исключены; вопрос в начале («С чем помочь?») по-прежнему засчитывается.

Тесты: 74 (+6, все на придуманных мини-диалогах, не на DEV).

Контрольные прогоны (текущая разметка):

| | основной (19) | отложенный (15) |
|---|---|---|
| gemini-3.1-flash-lite, три последних прогона | 92.1 / 91.4 / 92.1% | 88.3 / 89.2 / 89.2% |
| gpt-4.1-mini, три последних прогона | 90.8 / 91.4 / 89.5% | 85.8 / 87.5 / 84.2% |

Целевые случаи починены (`p1-ru-002` c3, `p1-ru-025` c2). **gpt-4.1-mini нестабильна:** между прогонами меняются ответы

## 2.12 Звонки, общий путь, препроцессинг

## 4. Как мерить, чтобы не обмануть себя

1. Все пункты выше найдены на тех же 19 диалогах, на которых меряем. Чинить только то, что прямо следует из текста
   чек-листа (PDF), а не «чтобы совпало». Пункты 2.1, 2.2, 2.5 этому соответствуют; 2.4 и 2.7 требуют решения команды.
2. Разметить ещё 10–15 DEV-диалогов как отложенный набор и не смотреть на него, пока идут правки. Финальную цифру
   считать на нём.
3. Каждое изменение — отдельный прогон и запись «было / стало» по каждому критерию. Не помогло — откатить.
4. Дешёвый прогон для проверки правок: `--backend openai --model gpt-4.1-mini --workers 6` (~$0.09 и ~45 с на 19 диалогов).
   Финальное сравнение — на модели, которая пойдёт на контроль.
5. gpt-5.x принимают только temperature = 1, результат между прогонами плавает на ±1–2%. Делать 2–3 прогона.

## 5. Рассуждения (think) по критериям

Отдельный эксперимент на Qwen 9B, три прогона на 19 диалогах:
- без рассуждений (база 80.3%);
- `--think-on 04,06,07` — критерии на суждение, где разрыв с gpt-5.5 самый большой;
- `--think-on all`.

Оставлять рассуждение на критерии, если там +3 метки и больше без потерь на других; следить за временем на диалог.
Ожидание скромное: в наших прогонах рассуждающая gpt-5.4-mini оказалась хуже нерассуждающей gpt-4.1-mini.
